1. TỔNG QUAN & STACK CÔNG NGHỆ
---------------------------------------------------------------------
- Web tin tức có 2 phần: Admin panel (quản trị) và Frontend (giao diện
  người đọc, layout phỏng theo gocvacham.com nhưng đã tùy biến nhiều
  theo yêu cầu riêng - xem mục 11, 14).
- Stack: Node.js + Express + EJS (render HTML phía server, không phải
  SPA/React) + MongoDB (Mongoose ODM).
- Auth: session (express-session) + bcryptjs để hash mật khẩu.
- Upload ảnh: multer, lưu file thẳng vào ổ đĩa (public/uploads/).
- Không có Docker/container trong dự án này. Không cần "rebuild
  container" khi sửa code - chỉ cần sửa file và restart server (hoặc
  không cần restart nếu chỉ sửa file .ejs/.css/.js phía client trong
  public/, xem mục 16).

5. KẾT NỐI DATABASE (rất quan trọng - đọc kỹ để tránh mất thời gian)
---------------------------------------------------------------------
File: src/config/db.js

- Nếu MONGODB_URI có giá trị -> connect vào MongoDB thật đó, dữ liệu
  lưu bền vững như bình thường.

- Nếu MONGODB_URI để TRỐNG (mặc định lúc mới build xong dự án, VẪN
  ĐANG ĐỂ TRỐNG tính đến thời điểm viết bản cập nhật này) -> code tự
  spawn một MongoDB "in-memory" (thư viện mongodb-memory-server) chỉ
  tồn tại trong RAM của tiến trình node đang chạy.

  HỆ QUẢ CẦN NHỚ (đã xảy ra NHIỀU LẦN trong quá trình phát triển):
  * Mỗi lần restart server (tắt/bật lại `node src/server.js`, hoặc
    nodemon tự restart khi sửa file .js) -> TOÀN BỘ dữ liệu mất sạch
    (bài viết, danh mục, tiktok product, mật khẩu admin đã đổi qua màn
    "Đổi mật khẩu", lượt view/click thật đã tích lũy...).
  * Sau mỗi lần restart, server tự tạo lại 1 tài khoản admin mới từ
    ADMIN_USERNAME/ADMIN_PASSWORD trong .env (xem mục 7).
  * `npm run seed` chạy RIÊNG một tiến trình khác -> nếu đang ở chế độ
    in-memory thì seed sẽ tạo ra 1 DB in-memory KHÁC, không liên quan
    gì tới DB của server đang chạy. Script seed chỉ thực sự hữu ích
    khi có MONGODB_URI thật.
  * BẤT KỲ thay đổi code nào ở file .js (controller/model/route/app.js)
    đều cần restart server -> đều làm mất dữ liệu đang có trong phiên
    làm việc hiện tại. Đây là nguyên nhân của rất nhiều lần "tự nhiên
    mất hết bài viết/tiktok product" trong quá trình build/fix tính
    năng mới.

  MUỐN DỮ LIỆU LƯU LÂU DÀI (không mất khi restart):
  -> Cài MongoDB thật (mongod local, Docker, hoặc MongoDB Atlas free
     tier), rồi set MONGODB_URI trong .env, restart lại server.
     NÊN LÀM SỚM nếu chuẩn bị đưa nội dung thật lên.

6. DATA MODELS (Mongoose Schema) - CẬP NHẬT MỚI NHẤT
---------------------------------------------------------------------

Admin (src/models/Admin.js)
  username       String, unique
  passwordHash   String (bcrypt hash, KHÔNG lưu plaintext)

Category (src/models/Category.js)
  title          String
  slug           String, unique (tự sinh từ title bằng slugify)

TiktokProduct (src/models/TiktokProduct.js)
  title          String
  type           String (tự do, không enum cố định)
  image          String (đường dẫn "/uploads/xxx.jpg")
  tiktokLink     String (URL video/trang TikTok)
  clicks         Number, default 0 - CỘT MỚI, đếm số lần user bấm nút
                 "Xem trên TikTok" / nút X trong popup TikTok gate ở
                 trang chi tiết bài viết (xem mục 12). Tăng qua endpoint
                 POST /api/tiktok-click/:id (siteController.trackTiktokClick).
                 Admin xem/sort được cột này ở /admin/tiktok (mục 15).

SiteConfig (src/models/SiteConfig.js)  -- SINGLETON (chỉ có 1 document)
  logo           String (đường dẫn ảnh logo, hiển thị DẠNG TRÒN - xem
                 mục 14 - và LUÔN đi kèm chữ "TinTức24h" bên cạnh,
                 KHÔNG thay thế chữ)
  hotline        String
  Lấy config bằng SiteConfig.getSingleton() - tự tạo document rỗng nếu
  chưa có cái nào.

Article (src/models/Article.js)  -- MODEL QUAN TRỌNG NHẤT
  title            String
  slug             String, unique (dạng: slug-title + 6 ký tự cuối
                    của _id, để tránh trùng, sinh trong
                    articleController.uniqueSlug())
  (ĐÃ BỎ field "image"/ảnh đại diện riêng - xem lý do ở mục 18, bug #4.
   Ảnh đại diện/thumbnail hiển thị ở FE (trang chủ, danh mục, admin
   list) giờ LUÔN LẤY TỪ bodyImage1.)
  bodyParagraph1   String - đoạn văn 1. LUÔN hiển thị IN ĐẬM (<strong>)
                    ở FE (trang chi tiết + excerpt "Tin nổi bật" ở
                    trang chủ).
  bodyImage1       String - ảnh 1 (chèn giữa đoạn 1 và đoạn 2 trong bài
                    chi tiết). ĐỒNG THỜI dùng làm ảnh đại diện/thumbnail
                    ở mọi nơi khác trên FE và ở cột "Ảnh" trong admin
                    list bài viết.
  bodyParagraph2   String - đoạn văn 2
  bodyImage2       String - ảnh 2 (chèn giữa đoạn 2 và đoạn 3)
  bodyParagraph3   String - đoạn văn 3
  category         ObjectId ref Category (bắt buộc)
  views            Number, default 0, tự +1 mỗi lần có người xem
                    trang chi tiết (xem mục 12). Đây là số THẬT, dùng
                    để: (a) sort "Đọc nhiều nhất", (b) sort cột "Lượt
                    xem" trong admin. KHÔNG hiển thị số này trực tiếp
                    cho khách ở FE (xem mục 13 - số hiển thị FE là số ảo).
  status           Number, chỉ nhận 0 hoặc 1
                    1 = Tin chính (main news). Luôn được ƯU TIÊN hiển
                      thị: là ảnh to bên trái khối "Tin nổi bật" ở
                      trang chủ; và trong admin list bài viết, mọi bài
                      status=1 LUÔN bị/được ghim lên đầu danh sách (bất
                      kể đang search/sort gì) + có highlight nền xanh
                      dương nhạt (xem mục 15).
                    0 = Tin phụ (secondary, hiển thị trong "Tin mới nhất").
  tiktokProduct    ObjectId ref TiktokProduct, có thể null - nếu có
                    thì trang chi tiết sẽ hiện popup TikTok gate (mục 12)
  isTopNews        Boolean - đánh dấu bài thuộc khu "Tin nóng" (ticker
                    chữ ở đầu trang chủ, KHÔNG có ảnh - xem mục 11)
  createdAt/updatedAt  tự động (timestamps: true)

7. LUỒNG XÁC THỰC ADMIN (Auth)
---------------------------------------------------------------------
- File: src/controllers/admin/authController.js,
        src/middleware/auth.js,
        src/seed/ensureAdmin.js

- Khởi động server (src/server.js):
    connectDB() -> ensureAdmin() -> app.listen()
  ensureAdmin() kiểm tra: nếu CHƯA có admin nào trong DB thì tạo 1 cái
  từ ADMIN_USERNAME/ADMIN_PASSWORD (.env), hash password bằng bcrypt.
  Nếu ĐÃ có admin rồi thì bỏ qua (không ghi đè mật khẩu đã đổi).

- Login (POST /admin/login): so sánh bcrypt.compare(password nhập,
  admin.passwordHash). Nếu đúng -> lưu req.session.adminId, redirect
  vào /admin.

- Middleware requireAuth (src/middleware/auth.js): mọi route /admin/*
  (trừ /admin/login) đều check req.session.adminId, nếu không có thì
  redirect về /admin/login.

- Đổi mật khẩu (/admin/change-password): yêu cầu nhập đúng mật khẩu
  hiện tại, mật khẩu mới TỐI THIỂU 8 KÝ TỰ, xác nhận khớp. Lưu ý: mật
  khẩu ngắn hơn 8 ký tự (vd yêu cầu đặt "banhbao" - 7 ký tự) sẽ bị màn
  này từ chối; muốn đặt mật khẩu ngắn hơn 8 ký tự làm password MẶC ĐỊNH
  thì sửa trực tiếp ADMIN_PASSWORD trong .env rồi restart server (bootstrap
  lúc start KHÔNG kiểm tra độ dài).

  LƯU Ý: nếu đang chạy ở chế độ MongoDB in-memory (mục 5), đổi mật
  khẩu ở đây sẽ MẤT khi restart server (vì admin bị tạo lại từ .env).
  Muốn đổi mật khẩu vĩnh viễn phải dùng MongoDB thật.

8. UPLOAD ẢNH (Multer)
---------------------------------------------------------------------
File: src/middleware/upload.js

- Lưu file vào: public/uploads/ (đường dẫn tuyệt đối tính từ
  __dirname của file upload.js, đi lên 2 cấp rồi vào public/uploads).
- Tên file được đổi thành: <timestamp>-<6 byte random hex>.<đuôi gốc>
  để tránh trùng tên / ghi đè file cũ.
- Chỉ cho phép đuôi: .jpg .jpeg .png .gif .webp
- Giới hạn dung lượng: 5MB / file (multer limits.fileSize).
- File ảnh sau khi upload được serve tĩnh qua express.static ở
  app.js -> URL truy cập là "/uploads/<tên file>".

Nơi dùng upload.single() / upload.fields():
  - TikTok product form: upload.single('image')
  - Site config (logo): upload.single('logo') - logo hiển thị DẠNG
    TRÒN ở FE (mục 14), KHÔNG có tính năng "gỡ logo" - chỉ ghi đè bằng
    cách upload logo mới.
  - Article form: upload.fields([
      {name:'bodyImage1'}, {name:'bodyImage2'}
    ])  -- ĐÃ BỎ field 'image' (ảnh đại diện) khỏi đây, xem mục 6+18.
    Ảnh bodyImage1/bodyImage2 CÓ THỂ nhập bằng cách upload file HOẶC
    dán URL/đường dẫn trực tiếp (input bodyImage1Url / bodyImage2Url -
    type="text", KHÔNG phải type="url" - xem lý do ở mục 18 bug #5) -
    controller ưu tiên file upload nếu có, không thì lấy theo giá trị
    nhập tay.
  - Form admin có JS preview ảnh trực tiếp (public/js/admin.js): mọi
    input[type=file] có data-preview="<id>" sẽ tự hiện ảnh preview vào
    thẻ #<id> ngay khi chọn file, dùng URL.createObjectURL(). Input
    dạng "dán URL" có data-preview-url-for="<id>" cũng tự cập nhật
    preview khi gõ/dán.

9. ROUTES - ADMIN PANEL (src/routes/admin.js)
---------------------------------------------------------------------
Auth:
  GET  /admin/login              form đăng nhập
  POST /admin/login               xử lý đăng nhập
  POST /admin/logout              hủy session
  GET  /admin/change-password
  POST /admin/change-password

Dashboard:
  GET  /admin                     hiện tổng số bài viết/danh mục/tiktok

Categories:
  GET  /admin/categories
  GET  /admin/categories/new
  POST /admin/categories
  GET  /admin/categories/:id/edit
  POST /admin/categories/:id       (update)
  POST /admin/categories/:id/delete
  (Danh mục KHÔNG có search/sort/phân trang - chỉ articles và tiktok
   có, theo yêu cầu.)

TikTok products:
  GET  /admin/tiktok               ?q=&sort=clicks_asc|clicks_desc&page=N
                                    20 sản phẩm/trang (PER_PAGE trong
                                    tiktokController.js)
  GET  /admin/tiktok/new
  POST /admin/tiktok                upload.single('image')
  GET  /admin/tiktok/:id/edit
  POST /admin/tiktok/:id            upload.single('image')
  POST /admin/tiktok/:id/delete

Articles:
  GET  /admin/articles              ?q=&sort=views_asc|views_desc&page=N
                                    20 bài/trang (PER_PAGE trong
                                    articleController.js). Mọi query đều
                                    tự động ghim status=1 lên đầu (sort
                                    Mongo: { status: -1, ...sortPhu }).
  GET  /admin/articles/new
  POST /admin/articles               upload.fields(bodyImage1, bodyImage2)
  GET  /admin/articles/:id/edit
  POST /admin/articles/:id           upload.fields(bodyImage1, bodyImage2)
  POST /admin/articles/:id/clone     NHÂN BẢN bài viết - copy toàn bộ
                                    field (trừ slug/_id/views), title
                                    thêm hậu tố " (Bản sao)", slug mới
                                    sinh riêng, views về 0.
  POST /admin/articles/:id/delete

Site config:
  GET  /admin/config
  POST /admin/config              (logo + hotline) upload.single('logo')

Cơ chế search/sort/pagination (giống nhau cho cả articles & tiktok):
  - q: tìm theo title, dùng $regex + $options:'i' (không phân biệt hoa
    thường), có escapeRegex() (src/utils/text.js) để tránh regex bị
    lỗi/injection khi user gõ ký tự đặc biệt (. * + ? ...).
  - sort: chỉ nhận đúng 1 trong các giá trị hợp lệ (views_asc/
    views_desc cho articles; clicks_asc/clicks_desc cho tiktok) - giá
    trị khác bị bỏ qua, fallback về mặc định (createdAt desc).
  - page: mặc định 1, PER_PAGE=20 cho cả 2.
  - View dùng chung partial admin/partials/pagination.ejs để render
    số trang, tự giữ nguyên q & sort trong link chuyển trang.
  - Cột "STT" (số thứ tự) trong list KHÔNG phải _id, mà là số thứ tự
    liên tục theo trang: (page-1)*perPage + index + 1.

16. VIEWS (EJS) - CẢNH BÁO LỖI ĐÃ GẶP (RẤT QUAN TRỌNG)
---------------------------------------------------------------------
Mỗi trang EJS đều có cấu trúc:
  <%- include('partials/header', {...}) %>
  ... nội dung riêng của trang ...
  <%- include('partials/footer') %>

LỖI ĐÃ GẶP: Ban đầu code viết nhầm thành <% include(...) %> (thiếu
dấu gạch ngang "-"). Trong EJS:
  <%  ...  %>   = chạy code JS, KHÔNG in kết quả ra HTML (scriptlet)
  <%- ... %>   = chạy code và IN kết quả ra HTML, không escape
  <%= ... %>   = chạy code và in ra HTML CÓ escape (dùng cho text)

Vì include() trả về chuỗi HTML đã render, nếu đặt trong <% %> thì
chuỗi đó bị "vứt bỏ", không in ra gì cả -> hậu quả là header/footer
(chứa <head>, thẻ <link rel="stylesheet">, sidebar admin, menu
frontend...) HOÀN TOÀN BIẾN MẤT khỏi trang, chỉ còn lại nội dung ở
giữa, không có CSS, không có layout -> trông như HTML thô không style.

=> NẾU SAU NÀY THẤY TRANG NÀO "MẤT STYLE / MẤT SIDEBAR / MẤT MENU"
   MỘT CÁCH KỲ LẠ: việc đầu tiên cần check là các dòng include() ở
   đầu/cuối file .ejs đó có đang dùng đúng "<%- include(...) %>"
   hay không. Các icon dùng chung (icon-eye.ejs, icon-clock.ejs) cũng
   phải include bằng <%- %> tương tự.

Ngoài ra: Express mặc định KHÔNG cache view trong môi trường dev (chỉ
cache khi NODE_ENV=production) -> sửa file .ejs/.css/.js trong public/
KHÔNG cần restart server, chỉ cần load lại trang trên trình duyệt là
thấy thay đổi ngay. Nếu sửa file .js phía server (controller, route,
model, app.js, utils/...) thì BẮT BUỘC phải restart server (và nếu
đang ở chế độ MongoDB in-memory thì mất hết dữ liệu - xem mục 5).

(6) Chữ "TinTức24h" ở footer không đổi màu dù đã set CSS color đúng
    Nguyên nhân: lỗi CSS SPECIFICITY. Rule `.site-footer strong { color:
    #fff; }` (specificity: 1 class + 1 element = 0,1,1) có độ ưu tiên
    CAO HƠN rule `.site-footer__logo { color: var(--accent); }`
    (specificity: 1 class = 0,1,0), nên dù đặt SAU trong file CSS, rule
    màu trắng vẫn thắng (CSS specificity luôn thắng thứ tự source order
    khi 2 rule cùng áp dụng lên 1 phần tử). ĐÃ FIX: tăng specificity
    bằng cách viết lại selector cụ thể hơn: `.site-footer strong.site-
    footer__logo { color: var(--accent); ... }`.
    => BÀI HỌC: khi sửa màu/style 1 CLASS mà "không ăn" dù chắc chắn
       CSS đã lên server, luôn nghi ngờ CSS SPECIFICITY trước (có rule
       khác cụ thể hơn đang đè lên không), không phải do cache/chưa
       reload.

    Nguyên nhân: MONGODB_URI để trống -> mỗi lần sửa file .js (bắt

Khi debug lỗi mới, luôn kiểm tra theo thứ tự:

  b. Đang dùng MongoDB in-memory hay MongoDB thật (mục 5) - rất nhiều

  c. Nếu là lỗi hiển thị (mất style/mất phần tử) -> check include()
